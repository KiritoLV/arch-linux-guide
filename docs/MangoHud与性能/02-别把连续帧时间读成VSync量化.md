# 分析帧时间时最容易犯的错：把连续分布读成「VSync 量化」

!!! info "一句话"
    按刷新率整数倍分桶，会把正常的 13 ms 帧全塞进「2 拍」桶，从而得出完全错误的结论。

## 现象

文件里 73% 的帧落在「2 个刷新间隔」、25% 落在「3 个」，于是判定「帧被锁在 170 Hz 节拍上、
游戏 vsync 在量化、开 VRR 也没用」。

## 环境

170 Hz 输出（一个刷新间隔 5.882 ms）；任何 MangoHud frametime CSV。

## 排查

**错误做法**（会得出假结论）：

```python
bucket = round(frametime_ms / 5.882)     # 桶宽 5.882 ms！
# 10.0–14.7 ms 全部落进 bucket=2 → 看起来「73% 命中 2 拍」
```

**正确做法**，三条一起看：

```python
# ① 细粒度直方图（0.5 ms 一格）—— 连续单峰就说明没有锁拍
# ② 落在整数拍 ±0.3 ms 内 的比例：真锁拍 >80%
rate = sum(1 for x in ft if abs(x/5.882 - round(x/5.882))*5.882 < 0.3) / len(ft)
# 本机实测：VRR 开 7.2%，VRR 关 10.9%  → 根本没有量化
# ③ 短帧(<12.5ms)/长帧(>16.5ms) 的相邻切换次数 —— 纯 2/3 拍交替会显著偏高
```

## 原因

桶宽太大。5.882 ms 的桶边界落在 8.8 / 14.7 / 20.6 ms，正常 13–14 ms 的帧必然整段落进
「2 拍」，于是**任何**数据都会显示「量化」。

## 解决办法

改判据：细粒度直方图看形状 + ±0.3 ms 贴合率 + 短长帧交替计数。

另外三条同样重要的读法：

- MangoHud 的 `frametime` 是**游戏内部帧间隔**，看不到显示侧 VRR 的跟随效果；
  判 VRR 只能靠 `niri msg --json outputs` 的 `vrr_enabled` + 体感。
- 两份 CSV 不是同一场景时，**帧率差 2–3、p99 差 1–2 ms 都算噪声**；先比 GPU 占用与温度。
- GPU 92% 满载时，每帧渲染 14 ms 远大于 5.88 ms 的刷新间隔，VSync 想量化也量化不出来。

## 怎么确认好了

真锁拍的数据长这样：>80% 的帧落在整数拍 ±0.3 ms；本机任何一组都只有 7–11%。
