# 03 显卡与显示

> 最后核对：2026-11-24。这是全本机最容易出问题的一章，改任何一项先读完再动手。

## 1. 拓扑（一切结论的前提）

| DRM | 设备 | PCI | 接口 | 日常状态 |
|---|---|---|---|---|
| `card0` | NVIDIA RTX 4060 Laptop | `01:00.0` | **DP-9**（外接 H27T22S） | 扫描输出 |
| `card1` | AMD Radeon 780M | `66:00.0` | eDP-1（内屏） | 默认关闭 |

```bash
lspci -nn | grep -E "VGA|3D"
for c in /sys/class/drm/card[0-9]/device/vendor; do echo "$c: $(cat $c)"; done
niri msg outputs                     # 谁在输出、刷新率、VRR 状态
ls -l /proc/$(pgrep -x niri)/fd | grep -oE 'renderD[0-9]+' | sort -u   # niri 实际用哪个节点
```

**外接屏物理上接在 4060 的口上**，这是本机所有「跨卡」问题的根源。

## 2. 两档：`niri-gpu-profile`

```bash
niri-gpu-profile status
niri-gpu-profile normal    # 桌面走核显（省电），之后要退出登录重进
niri-gpu-profile game      # 全 4060（游戏档），之后要退出登录重进
```

| 档位 | niri 合成卡 | `render-drm-device` | 锁频 | `wait-for-frame-completion-before-queueing` |
|---|---|---|---|---|
| `normal` | 780M（`ignore-drm-device` 屏蔽 4060） | — | 不锁 | **不加**（同卡，没有跨卡合成） |
| `game` | 4060 `renderD129` | 有 | 锁 840 地板 | **加**（压跨卡撕裂） |

脚本只重写 `config.kdl` 里 `// >>> GPU-PROFILE BEGIN` 与 `// <<< GPU-PROFILE END` 之间的内容 ——
**需要按档位切换的 debug 选项必须写进脚本的 `PROFILES[...]["lines"]`，写在块外会被切档无视。**

**顺序固定：先改配置 → 再换线 → 最后退出登录重进。** 反过来会黑屏（目标口拿不到 modeset）。

## 3. Chrome 为什么必须跑 780M

Chromium 的 VA-API 主动跳过 NVIDIA：

```
media/gpu/vaapi/vaapi_wrapper.cc:131
WARNING: Should skip nVidia device named: nvidia-drm
```

所以 `chrome://gpu` 上 `Video Decode: Hardware accelerated` 是**假象** ——
`Video Acceleration Information → Decoding:` 是**空的**，实际还在软解。

```
# ~/.config/chrome-flags.conf（wrapper 用 grep -v '^#' 过滤注释，写中文注释安全）
--render-node-override=/dev/dri/renderD128      ← 780M 的 render 节点
```

实测（780M 真硬解，B 站视频 + 弹幕）：

| 项 | 数值 |
|---|---|
| `GL_RENDERER` | `ANGLE (AMD, AMD Radeon 780M Graphics (radeonsi phoenix ACO)…)` |
| `Decoding:` | h264 / vp9 / hevc / av1 全列出来 |
| Chrome 合计 CPU | 51%（GPU 被整关时是 102%，别把那种"降 CPU"当优化） |
| CPU Tctl | 52.4–53.8 ℃ |
| 风扇 | 3700–3800 RPM |

**`--use-gl=egl` 在 Chrome 158 是非法值**，会让 GPU 完全失效（全软件渲染）：

```
gl_factory.cc:110 Requested GL implementation (gl=egl-gles2, angle=none) not found in
allowed implementations: [(gl=egl-angle,angle=opengl), (gl=egl-angle,angle=opengles),
(gl=egl-angle,angle=vulkan)]
```

`--disable-frame-rate-limit` 只能做诊断：解除 vsync 后 renderer 103% / gpu 130% CPU、
Tctl 94 ℃、风扇 6000 RPM，不能日常用。

## 4. 跨卡撕裂与 `wait-for-frame-completion-before-queueing`

**根因**：niri 没有 `linux-drm-syncobj-v1`（explicit sync）。Chrome 在 780M 渲染、niri 在 4060
扫描输出，跨卡 dmabuf 只能隐式同步。判据：

```bash
# Chrome 日志里
WARNING:ui/ozone/platform/wayland/host/wayland_drm.cc:114 : Drm prime capability is not supported
```

上游状态（2026-11-24 实测 GitHub）：issue #843 自 2024-12 开着；PR #3956（2026-05 提出，+186/−59）
**0 review**，主分支搜 `syncobj` 无代码。→ 短期不会合并，只能 workaround。

**workaround 就是 game 档那条 debug 选项**，它每帧现读配置，**支持热重载**：

```bash
niri validate -c ~/.config/niri/config.kdl
niri msg action load-config-file
journalctl --user -b | grep "niri_config: loaded" | tail
```

代价与本机 A/B（PBZ，170 Hz，各 200/383 秒）：

| | 开 | 关 |
|---|---|---|
| fps 平均 | 72.3 | 69.3 |
| p99 帧时间 | 20.44 ms | 21.65 ms |
| GPU 占用 | 90% | 92%（那局场景更重） |

→ **差 3 帧 / 1.2 ms 属场景噪声**，测不出代价。社区 30 个 issue 全是"加了修好花屏/撕裂"，
唯一负面是 #3774 在 **300 Hz**（3.33 ms 预算）报告顿挫；170 Hz 无相关抱怨。

## 5. VRR：规则写错了一年都没生效

DP-9 支持 VRR，配置是 `on-demand=true`（桌面不触发，避免 48↔170 亮度闪烁）+ 窗口规则放行。

**坑：Proton/XWayland 游戏的真实 app_id 是 `*.exe`，不是 `steam_app_<appid>`。**
本机 PBZ 实测 `pbz.exe`，而原来的规则写的是 `match app-id="^steam_app_"` → **从没命中过**，
`vrr_enabled` 一直 False。

```bash
niri msg --json windows | python3 -c "import json,sys;[print(w['app_id']) for w in json.load(sys.stdin)]"
niri msg --json outputs | python3 -c "import json,sys;[print(n,o['vrr_enabled']) for n,o in json.load(sys.stdin).items()]"
```

正确写法（一条覆盖所有 Proton 游戏）：

```kdl
window-rule {
    match app-id=r#"^.*\.exe$"#
    variable-refresh-rate true
}
```

**语义（源码级，别再猜）**：`niri-config/src/window_rule.rs` 的 `VrrRule` 有 `Off` / `On` /
`FullscreenOnly`；`true` 解析成 **`On` = 窗口可见即启用，不要求全屏**；`"fullscreen-only"` 才是
只在当前全屏窗口时启用。判定在 `src/niri.rs:5203 refresh_on_demand_vrr()`。
XWayland 客户端报 `creating toplevel … fullscreen: false` **不影响** `On` 规则。

热重载即可生效，游戏不用退（实测游戏跑着时从 False 变 True）。

**注意**：MangoHud 的 `frametime` 是游戏内部帧间隔，看不到 VRR 的显示侧效果；
判 VRR 只能靠 `vrr_enabled` + 体感。

## 6. 锁频（game 档 840 地板）

```bash
nvidia-smi --query-gpu=clocks.sm,clocks.current.memory,pstate,power.draw --format=csv,noheader
nvidia-clock-lock on / off        # 免密 wrapper；地板默认 GFX_MIN_DEFAULT=840
```

- **判据永远是 P-state，不是核心频率**：P0 和 P4 下核心可能都是 2250，差的是显存档。
- 完全不给下限会掉到 P8 / 300 MHz / 显存 405 → 高刷桌面直接顿，比低地板更糟。
- 本机 620.73.04 实测：地板 840 → P5 / 840 / 显存 810（约 10 W）；不需要额外钉显存（`-lmc`）。
- 锁频是**易失**的，重启后靠 `niri-gpu-profile resume` 在 `spawn-at-startup` 里按档位重下
  （`normal` 档什么都不做）。

## 7. MangoHud：记录与读法

```
# ~/.config/MangoHud/MangoHud.conf 关键几行
output_folder=~/mangologs     ← 目录不存在就永远不落盘（踩过）
autostart_log=5                          ← 启动 5 秒后自动开始，不用手动按 Shift+F2
pci_dev=0000:01:00.0                     ← 锁 4060，别让 MangoHud 抓错卡
```

CSV 结构：`v1` / `v0.8.4` / SYSTEM INFO 7 列 / **FRAME METRICS 16 列**
（`fps,frametime,cpu_load,cpu_power,gpu_load,cpu_temp,gpu_temp,gpu_core_clock,gpu_mem_clock,
gpu_vram_used,gpu_power,ram_used,swap_used,process_rss,cpu_mhz,elapsed`，`elapsed` 纳秒）。
旁边有 `_summary.csv`（MangoHud 自算 0.1%/1% low）。

**分析铁律（踩过，最贵）**：**不要用「按 1000/刷新率 的整数倍分桶」判断量化** ——
5.882 ms 的桶宽会把 10–14.7 ms 整段塞进「2 拍」，把正常的 13 ms 帧读成 VSync 锁拍。
正确判据三条一起看：

1. 细粒度直方图（0.5 ms 一格）看形状 —— 连续单峰 = 没锁拍；
2. 落在整数拍 ±0.3 ms 内的比例 —— 真锁拍 >80%，本机实测只有 7–11%；
3. 短帧(<12.5 ms)/长帧(>16.5 ms) 的相邻切换次数。

**两份 CSV 不是同一场景时，帧率差 2–3、p99 差 1–2 ms 都算噪声。** 先比 GPU 占用与温度，
占用更高的那局慢是正常的。

## 8. 游戏性能基线（PBZ，2560×1440，170 Hz，game 档）

| 指标 | 数值 |
|---|---|
| fps 平均 / 1% low | 69–73 / 36–43 |
| 帧时间 中位 / p99 | 13.5–14.4 ms / 20–22 ms |
| GPU 占用 / 频率 | **92–95%** / 2419–2490 MHz |
| GPU 温度 / 功耗 | 81–87 ℃ / 81–84 W |
| **CPU 温度** | **92 ℃ 均，峰值 97 ℃**（负载只有 30%） |
| >33 ms 的帧 | 308 秒里 10 个（0.05%） |

结论：**GPU 满载是硬瓶颈**（74 fps 天花板），帧节奏很干净；CPU 温度是散热侧的问题，
与显卡无关。想提帧数只能降画质或换机器，不是调参数能救的。
